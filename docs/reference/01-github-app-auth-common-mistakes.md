# GitHub App Auth — Common Mistakes and How to Avoid Them

This document records real configuration errors and code bugs discovered during the implementation
and testing of the MOREL auth system. Each issue caused significant debugging time and produces
non-obvious error messages from GitHub.

______________________________________________________________________

## 1. Configuration mistakes

### Typo in `GITHUB_OAUTH_REDIRECT_URI`

The redirect URI in Infisical must be an exact character-for-character match with the callback URL registered in the GitHub App settings and the `redirect_uri` the worker sends during token exchange. A single-character typo (e.g. `auth/callbac` instead of `auth/callback`) causes GitHub to reject the exchange with a cryptic error. Always verify the value in Infisical directly after setting it by running:

```sh
infisical export --env=dev --path=/workers/auth --format=dotenv
```

### GitHub App set to "Only on this account"

Under *"Where can this GitHub App be installed?"*, the default is *"Only on this account"*.
This prevents any account other than the owner from installing the app, causing a 404 on the authorize page for all other users. For a real-world app, this must be changed to *"Any account"* before testing with any non-owner GitHub account.

### Wrong callback URL order when using multiple environments with one GitHub App

The GitHub App installation redirect always uses the **first** registered callback URL — it does not accept a `redirect_uri` parameter like the OAuth authorize endpoint does. If the staging or production URL is listed first, local dev installation callbacks will land on the wrong environment.

Always put the most-used development URL first:

```plaintext
http://localhost:5173/auth/callback      ← first (used for local dev installation redirect)
https://your-staging-url/auth/callback  ← second
```

The recommended approach for production is to use **separate GitHub Apps per environment** so callback URL ordering is never a concern.

### Wrong GitHub App slug

The slug used in installation URLs (`https://github.com/apps/{slug}/installations/new`) is
auto-generated by GitHub from the app name and may differ from what you expect. Always get the
slug from the app's actual URL on GitHub, not from the app name. Hardcoding a guessed slug will
produce a 404 with no explanation.

The slug is read from `VITE_GITHUB_APP_SLUG` in Infisical at path `/apps/web`:

| Infisical env | Value |
| -- | -- |
| `dev` + `staging` | `morel-studio-dev` |
| `production` | `morel-studio` |

In code it is exposed as:

```ts
// apps/web/src/features/auth/hooks/useGitHubAuth.ts
export const GITHUB_APP_SLUG = import.meta.env.VITE_GITHUB_APP_SLUG as string;
```

## 2. Code bugs

### React Strict Mode double-invocation breaks sessionStorage-based state handoff

In development, React Strict Mode mounts, unmounts, and remounts every component, running effects
twice. Any `useEffect` that reads and removes a one-time value from `sessionStorage` will consume
it on the first mount and find nothing on the second mount, silently failing.

Fix: add a `useRef` guard at the top of the effect body.

```ts
const hasRun = useRef(false);

useEffect(() => {
  if (hasRun.current) return;
  hasRun.current = true;
  // ... rest of effect
}, []);
```

The same problem affects effects that schedule async work via `requestAnimationFrame`: Strict
Mode's cleanup phase calls `cancelAnimationFrame` before the second mount can run the frame.
Replace `requestAnimationFrame` with a direct async call when the work must survive the remount
cycle.

### Missing logger methods crash silently in catch blocks

If a logger method that does not exist is called inside a `catch` block, the resulting `TypeError`
is swallowed by that same `catch`, making the original error completely invisible. The symptom is
a feature that silently does nothing.

Always keep the logger interface and its implementation in sync. The `authLogger` interface is
defined in `apps/web/src/features/auth/lib/authLogger.ts` — add a method to both the interface
and the implementation at the same time.

### `listInstallationsForAuthenticatedUser()` returns a wrapper object, not an array

The Octokit response for `apps.listInstallationsForAuthenticatedUser()` is shaped as:

```ts
{ total_count: number, installations: Installation[] }
```

Calling `.some()` directly on `data` (the wrapper object) throws a `TypeError` at runtime rather
than returning `false`. Always destructure the nested array:

```ts
// Wrong
const { data: installations } = await octokit.rest.apps.listInstallationsForAuthenticatedUser();
installations.some(...); // TypeError

// Correct
const { data } = await octokit.rest.apps.listInstallationsForAuthenticatedUser();
data.installations.some(...);
```

## 3. Design gaps

### OAuth and Device flows authorize but do not install the GitHub App

The OAuth authorize endpoint (`/login/oauth/authorize`) and the Device Flow both grant a user
token but do **not** install the GitHub App on the user's account. Without an installation, the
token has no repository permissions and all API calls return 403.

After obtaining a token via any non-PAT flow, always check installation status and redirect if
needed:

```ts
const { data } = await octokit.rest.apps.listInstallationsForAuthenticatedUser();
const installed = data.installations.some((i) => i.app_slug === GITHUB_APP_SLUG);

if (!installed) {
  window.location.href = `https://github.com/apps/${GITHUB_APP_SLUG}/installations/new`;
}
```

### GitHub App "Authorize" button should redirect to the installation page, not the authorize page

Using `/login/oauth/authorize` for the GitHub App flow only authorizes the user — it does not
install the app. The correct entry point is `/apps/{slug}/installations/new`, which combines
installation and user authorization in one step (provided *"Request user authorization during
installation"* is enabled on the app settings page).

PKCE is not supported on the installation endpoint. This means `codeVerifier` must be treated as
optional throughout the entire exchange pipeline:

- Zod schema: `codeVerifier: z.string().optional()`
- Callback handler: only include `codeVerifier` in the exchange body if it is present
- Worker token exchange: only append `code_verifier` to the upstream params if provided
